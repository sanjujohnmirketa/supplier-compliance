# Response to Competitive Gap Report — Near-Term, Verified Action Items

**Status:** the user supplied an external comparison report (custom engine vs. Agentforce
vs. Coupa SIM/Risk Assess), well-researched and well-cited. Per the user's explicit
choice, this doc extracts only the near-term, verifiable items and checks them against
the actual current codebase — it does NOT adopt the report's full recommendation list
(SOC 2, ERP connectors, EU AI Act scoping, etc.) as near-term work. Those remain a
separate, later "strategic roadmap" conversation if/when the business decides to pursue
them.

---

## 1. Correction to the report's baseline description

The report states: *"No specific model architecture, datastore, or ERP connector has
been fixed yet."* This is not accurate for the current implementation and is worth
correcting before this report circulates further:

- **Datastore is fixed**: Postgres + pgvector, deployed to Azure Database for PostgreSQL
  Flexible Server (per the Azure deployment walkthrough earlier this engagement).
- **Model is fixed**: `gpt-4o` via `llm.py`'s provider-agnostic `chat_json()` interface
  (provider-swappable by design, but not "unfixed" — a deliberate abstraction, not an
  open question).
- **ERP connector**: genuinely not yet built — this part of the report is accurate.

## 2. PII masking before LLM calls — verified, NOT a gap (report's implied concern doesn't apply)

The report highlights (correctly, as a real Salesforce behavior) that Salesforce's own
Einstein Trust Layer disables data masking for agents, and recommends this platform avoid
replicating that trade-off. **Verified against the actual code**: this platform already
does the right thing, and does it more thoroughly than the report's framing implies.

- `governance.py` (`governed_judge`) is documented in its own header as *"the single
  chokepoint that makes every LLM call over UNTRUSTED [text]"* run through
  `tokenize_pii()` first ([governance.py:44](../governance.py#L44)) — the LLM only ever
  sees `safe_text` (post-tokenization), never the raw untrusted document text.
- `/assess` (the endpoint that judges uploaded supplier documents — the actual untrusted-
  content path) calls `governance.governed_judge`, confirmed via
  [app.py:985](../app.py#L985).
- **Checked specifically because it looked like a possible gap**: `/copilot`
  ([app.py:792](../app.py#L792)) calls `llm.chat_json` directly, NOT through
  `governance.governed_judge`. On inspection this is correct, not an oversight — the
  co-pilot's `context`/`case_block` is built from **prior `/assess` findings**
  ([app.py:747-752](../app.py#L747-L752)), which were themselves generated by an LLM that
  only ever saw tokenized text. Grepped the whole codebase for any `detokenize` /
  `pii_map[...]` reverse-lookup — **none exists anywhere**. PII stays tokenized end-to-end
  once it enters the governed path; there's no code path that could re-inject raw PII
  into a later `/copilot` call.

**Conclusion**: no action needed here. This is a case where the report's general
industry-pattern warning doesn't apply to this specific implementation — worth stating
explicitly so this isn't mistakenly treated as an open item later.

## 3. Salesforce↔Azure transport pattern — the report's concern is real and current, not just an ERP-future concern

The report recommends *"use Platform Events or asynchronous REST callouts (not
synchronous, given the 25-concurrent-long-running-request ceiling)."* **Verified against
the actual code**: every current engine-calling service —
[ScopeService.cls](../supplierCompliance/force-app/main/default/classes/ScopeService.cls),
[DocAssessService.cls](../supplierCompliance/force-app/main/default/classes/DocAssessService.cls),
[PolicyIngestService.cls](../supplierCompliance/force-app/main/default/classes/PolicyIngestService.cls)
— uses a **synchronous `new Http().send()` call inside a Queueable**. This is correctly
async at the *Salesforce job* level (Queueable, not a trigger-blocking callout — which
Salesforce disallows anyway), but the actual HTTP call itself is a blocking, synchronous
request-response, not a fire-and-forget/Platform-Event pattern.

**Why this matters concretely, not just theoretically**: `/assess` and `/policy/ingest`
can genuinely run for many seconds (LLM call + embedding generation), and each such call
occupies one of Salesforce's limited concurrent long-running-request slots for its full
duration. At today's usage volume (a handful of procurement users) this is not an active
problem — but it is a real, load-bearing architectural fact worth tracking as the
supplier base and concurrent-user count grow, not deferring indefinitely.

**Recommendation — flagged as a decision point, not actioned yet**: if/when concurrent
usage grows (e.g. once the Lead-driven sourcing flow and daily compliance batch in
`solution-design-lead-driven-sourcing-and-platform-consolidation.md` are both live,
meaningfully increasing callout volume), revisit whether `DocAssessQueueable`/
`ScopeCalloutQueueable`/`PolicyIngestQueueable`'s synchronous-callout-in-a-Queueable
pattern needs to move to a genuine async pattern (Platform Event published from
Salesforce → engine polls or an Azure Function/queue consumes it → writes the result back
via a separate callback callout). Not recommended as urgent work today — the current
Queueable pattern is a legitimate, working design for current scale, just not the
report's ideal end-state.

## 4. What this does NOT include (deliberately deferred, per user's choice)

The report's other recommendations — SOC 2 Type II attestation, named ERP connector

Agentforce-Testing-Center-equivalent evaluation harness, approval-chain amount-banding

the current build queue.
